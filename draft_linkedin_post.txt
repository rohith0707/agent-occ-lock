If you run parallel LLM agents writing back to a shared state, you've almost certainly hit a lost update problem.

We ran a quick benchmark with 25 concurrent subagents yesterday. Each agent took a 25ms pause to simulate model reasoning, then wrote its findings to shared memory.

With standard dictionary overwrites:
24 out of 25 writes were silently wiped out.
That's 96% data loss.
The slowest agent simply stomped everything that'd finished before it.

The usual fix is a Redis lock or mutex across the tool call. But when agents wait 1 to 3 seconds for a model response, pessimistic locking kills concurrency. It turns parallel agents into a slow sequential queue. Worse, if an agent times out, you're stuck debugging distributed deadlocks.

I didn't want the latency penalty, so I put together a tiny zero-dependency library to test an alternative: Optimistic Concurrency Control (OCC) with 3-way delta reconciliation.

Here's how we set it up:
1. Every read carries an immutable revision token (etag).
2. On commit, if the version advanced while the agent was thinking, it runs a 3-way diff between base, current, and incoming changes.
3. If the fields don't overlap (e.g. Agent 1 updated sentiment while Agent 2 updated tags), it auto-merges without re-running the model.
4. If there's an actual key collision, it backs off with jitter and retries with fresh state.

In the exact same 25-worker test:
0 lost updates. 100% state retention. No lock contention.
